# Need for synchronization

A program's code implies a sequential order of operations, but the compiler is free to reorder or transform them under optimization, as long as the observable result matches unoptimized execution.

Due to this, plus the [[15. concurrency|concurrency]] of modern computers, assumptions about a program's actual execution order are often wrong.

## Reasons for out-of-order execution

- **Compiler [[reordering instructions]]**
- **Out-of-order execution within a single processor**: modern CPUs execute instructions non-sequentially ([[superscalar execution]]) even though the machine code is sequential. Handled transparently by the CPU.
- **Multiple hardware threads running concurrently**: needs explicit synchronization:
    - memory fences — ensure memory accesses become visible to other CPUs in the right order.
    - atomic operations — ensure concurrent access to the same memory location doesn't cause undefined behavior.

# Higher-level synchronization objects

Most of the low-level synchronization primitives are quite error-prone and inconvenient to use.
Rust standard library exposes some higher-level synchronization objects.

## Arc<T>

- A thread-safe reference-counting pointer.
- ‘Arc’ stands for ‘Atomically Reference Counted’.

`Arc<T>` type provides shared ownership of a value of type `T`, allocated in the heap.

Invoking `clone` on `Arc` produces a new Arc instance, which points to the same allocation on the heap as the source Arc, while increasing a reference count. When the last `Arc` pointer to a given allocation is destroyed, the value stored in that allocation (often referred to as “inner value”) is also dropped.

### Mutability

Shared references in Rust disallow mutation by default, and `Arc` is no exception: you cannot generally obtain a mutable reference to something inside an `Arc`. 

If you do need to mutate through an Arc, you have several options:
- Use [[interior mutability]] with synchronization primitives like [[Mutex]], [[RwLock]], or one of the [[Atomic types]].
- Use clone-on-write semantics with Arc::make_mut which provides efficient mutation without requiring interior mutability. This approach clones the data only when needed (when there are multiple references) and can be more efficient when mutations are infrequent.
- Use Arc::get_mut when you know your Arc is not shared (has a reference count of 1), which provides direct mutable access to the inner value without any cloning.

## Mutex

Mutual Exclusion mechanism ensures that at most one thread at a time is able to access some data.

### Poisoning

> [!INFO] Idea
> Mutex becomes poisoned if it recognizes that the thread holding it has panicked.



## RwLock

Provides a mutual exclusion mechanism which allows multiple readers at the same time, while allowing only one writer at a time. In some cases, this can be more efficient than a mutex.


## Condvar

Condition Variable, providing the ability to block a thread while waiting for an event to occur.

## Barrier

Ensures multiple threads will wait for each other to reach a point in the program, before continuing execution all together.

> [!EXAMPLE]
> ```rust
> use std::sync::Barrier;
> use std::thread;
> 
> let n = 10;
> let barrier = Barrier::new(n);
> thread::scope(|s| {
>     for _ in 0..n {
>         // The same messages will be printed together.
>         s.spawn(|| {
>             println!("before wait");
>             barrier.wait();
>             println!("after wait");
>         });
>     }
> });
> ```
## mpsc

Multi-producer, single-consumer queues, used for message-based communication. Can provide a lightweight inter-thread synchronisation mechanism, at the cost of some extra memory.

## mpmc

Multi-producer, multi-consumer queues, used for message-based communication. Can provide a lightweight inter-thread synchronisation mechanism, at the cost of some extra memory.

## Once

Used for a thread-safe, one-time global initialization routine. Mostly useful for implementing other types like OnceLock.

## OnceLock

Used for thread-safe, one-time initialization of a variable, with potentially different initializers based on the caller.

## LazyLock

Used for thread-safe, one-time initialization of a variable, using one nullary initializer function provided at creation.
