# Lifetime

A *lifetime* is a named region of code within which a reference is guaranteed [[8. pointers and borrowing#Rules of References|valid]], enforced by the compiler's borrow checker.[^nomicon]

A lifetime begins where its reference is created and ends at its last use — not necessarily at the end of the lexical scope containing it.[^rbe] Only exception is if the referenced value implements `Drop`, running the destructor counts as a final use, so the lifetime extends to the end of the enclosing scope regardless.[^nomicon]

## Purpose

The borrow checker compares the lifetime of a reference to the lifetime of the data it refers to, and rejects any program in which a reference could outlive the value it points to (a dangling reference).[^book]

## Coarseness of the checker

The checker does not reason about types such as `Vec` or about which paths a reference addresses — only about named lifetime regions.[^nomicon] Consequently, some memory-safe programs are rejected because the checker cannot see that a reference does not alias a separate mutable borrow.[^nomicon] A single variable binding may also carry two lifetimes in succession (e.g., reassignment inside a loop), described as one lifetime ending and another beginning on the same variable.[^nomicon]

## Annotation

Explicit annotation is required only when the relationship between multiple references' lifetimes is ambiguous; otherwise lifetimes are inferred.[^book] Names begin with `'`, placed directly after `&` (e.g., `&'a i32`, `&'a mut i32`). Annotations do not alter how long a value lives — they only declare it.[^book]

### Lifetime elision

Elision rules applied to a signature before explicit annotation is required:[^book][^elision]

1. Each reference parameter receives its own lifetime.
2. If there is exactly one input lifetime, it is assigned to all elided output lifetimes.
3. If one parameter is `&self` or `&mut self`, its lifetime is assigned to all elided outputs.

If ambiguity remains afterward, compilation fails — the rules cover common patterns, not full inference.[^elision] `'_` serves as an explicit placeholder for an elided lifetime.[^elision]

### `'static`

Denotes a reference valid for the entire program.[^book]

String literals are `'static`, as their text is stored in the binary.

> [!TIP]
> A compiler suggestion to use `'static` typically indicates a dangling reference or an unrelated lifetime mismatch elsewhere; substituting `'static` is rarely the correct fix.[^book]

## Lifetime [[12. generics#Bounds|bounds]]

- `'a: 'b` denotes that `'a` outlives `'b`: `'a` lasts at least as long as `'b`.[^bounds]
- `T: 'a` denotes that every lifetime parameter contained in `T` outlives `'a`.[^bounds]
- **Implied bounds:** if a signature, struct, or `impl` block already contains `&'a T`, the compiler infers `T: 'a` without explicit statement.[^bounds]
- **Higher-ranked [[14. impl Trait type#Trait bounds|Trait bounds]]** (`for<'a> ...`) express a bound that must hold for all lifetimes — required, for instance, when a closure's reference has a lifetime shorter than any lifetime nameable in the enclosing signature.[^bounds]
